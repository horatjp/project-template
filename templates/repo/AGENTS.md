# AGENTS.md — AI協働ルール

## セッション開始

1. `docs/STATUS.md`(現在地)と `docs/learnings.md`(失敗と学び)を読む
   (`docs/STATUS.md` がテンプレートのまま未記入なら初期化がまだ — ヒアリングで `docs/requirements.md` を作り、
   `docs/PROJECT.md` と `docs/STATUS.md` を初期化するところから始める)。STATUS は `git log`・未コミット
   差分と照合し、未反映の進捗があれば補う。承認・検証済み・停止の状態は git から推測しない
2. 着手するタスクに対応するスペックが `changes/` にあればそれを読む(`_template/`・`archive/` は対象外)
3. 既存の設計・方針に関わる変更の前に、`docs/decisions/`・`docs/knowledge/`(いずれも
   `_template.md` は除く)・`docs/` の生きた文書(requirements.md・schema.md 等)を
   ファイル名と description で走査し、関係するものを読む
4. `status: deprecated`・`stale_after` 超過の記録は判断根拠にしない(超過を見つけたら
   更新か deprecated 化を提案する)。`stable` の決定はユーザー承認済みとして根拠にしてよい。`draft` の決定と
   未検証(`verified` なし)の knowledge は参考扱いとし、重要な判断の根拠にする前に検証する

## 変更の進め方

- `docs/rules/` に、触るパスを対象とする規約があれば先に読む
- 要件が曖昧なまま proposal を書かない。先にユーザーへ聞き切る
  (ワークスペースの hearing スキルがあれば、その方法論に従う)
- **スペック必須の変更**(新機能 / 公開インターフェース(API・DB スキーマ・CLI・画面構成)の変更 /
  `stable` な決定記録を覆す変更)は `changes/<change-name>/` で進める。どの区分でも proposal を書き、
  **ユーザーの明示的な承認を得てから**実装する。区分は proposal に理由付きで書き、承認で確定する:
  - **軽量** — 公開インターフェース・スキーマ・決定・セキュリティ・課金に触れない、タスク数件で収まる可逆な小機能。
    proposal だけで進め、実装メモ(方針・タスクと検証)と完了報告も proposal に書く。本人以外のAIの観点レビューは推奨。
    中断・再開だけでは区分は変わらない。スコープの拡大や調査で条件を外れたと分かったら標準に切り替え、design・tasks を足す
  - **標準** — 軽量に当たらないもの(破壊的・セキュリティ・課金に関わる変更、設計の検討が要る規模のものを含む)。
    承認後に design → tasks を書き、tasks の順に実装する。完了前に本人以外のAIによる観点レビューを受ける
    (観点の選び方は `.agents/skills/lens-review/SKILL.md`)
  - スコープ・影響範囲が proposal から変わったら、実装を止めて proposal を直し、再承認を得る。
    実装詳細レベルの乖離なら design(軽量は実装メモ)を直して現在形に保つ(完了報告の「判断した点」に記す)
- 上記に該当しない変更(バグ修正・微修正・内部リファクタリング)はスペック不要。直接実装してよい
- 承認ゲート hooks の検査は編集ツール経路のみで、シェル経由の書き込みは対象外
- 完了した change は、恒久的に効く判断が design・完了報告(軽量は proposal)にあれば
  `docs/decisions/` へ抽出してから `changes/archive/YYYY-MM-DD-<change-name>/`(完了日)へ移動する

## コードの設計

- 業務ルール・計算を担う関数・クラスは、実装の前に事前条件・事後条件・不変条件を書き出し、
  それに基づくテスト(境界値を含む)を先に書いてから実装する。条件に反する値は入口(引数検査・コンストラクタ)で弾く。
  書き先は design の契約節。軽量は proposal の実装メモ、スペック不要の変更はテスト名・docstring
- 副作用(引数・外部状態の書き換え、I/O)は名前とシグネチャに表れる場所へ分離し、それ以外は戻り値だけで結果を
  返す純粋関数・不変オブジェクトにする。名前に表れない処理を混ぜない
- テストが保証するのは書いた条件だけ。条件が要件から読み取れないときは推測せずユーザーに確認する
- 適用は業務ルールのあるコードに限る。UI・外部連携の配線や一度きりのスクリプトに抽象化を持ち込まない

## 記録

- **セッションをまたぐ情報伝達はファイルのみ。** 会話で伝えたことは存在しないものとして
  扱い、残す価値のある情報は都度ファイルに書き込む
- スキーマ・API仕様・要件など累積的な現在形は **`docs/` の生きた文書**(schema.md・api.md・
  requirements.md 等。frontmatter 不要。無ければ作る)に保ち、実装が完了したら実装済みの
  姿に更新する(未実装の承認済み差分は changes/ が持つ)。
  **「今どうなっているか」は生きた文書、「なぜそうしたか」は decisions**
- 後で再利用する非自明な知見(技術調査の結論・外部仕様の要点)・決定の根拠になった資料・再発し得る
  バグの原因と修正 → `docs/knowledge/` に1件1ファイル(書式は `_template.md`。単発の参照は作業報告で足りる)
- 方針・技術選定・設計を**決めた** → `docs/decisions/`。status(`draft` → ユーザー承認の確認後に `stable`)・
  既存の決定の覆し方・編集の扱いは `docs/decisions/_template.md` に従う
- **AI自身の作業のしかたで失敗した** → 修正の前に根本原因を分析し、`docs/learnings.md`
  冒頭のゲートを満たすなら追記してから直す(コード・システム側の不具合は knowledge へ)
- 記録の frontmatter(`generated`・`verified`・`stale_after` 等)は各 `_template.md` に従う。`verified` は
  **実際に中身を検証した主体**だけが付ける(自己検証・架空の検証者は不可)
- 学びが**規範に育ったら**昇格する(ユーザーに提案して承認を得る): 機械的に強制できる → hooks(Claude Code・
  Codex に登録済み。編集ツール経由の書き込みだけを検査)/ パス限定 → `docs/rules/` / 多段階の手順 →
  `.agents/skills/<name>/`(+ Claude Code 用に `.claude/skills/<name>` の symlink)/ それ以外 → この AGENTS.md。
  hooks を持たない CLI にも守らせたい規範は AGENTS.md に書く。昇格した learnings のエントリは1行に畳む
- 日付は環境の現在日付を確認して書く。記憶から推測しない
- 作業の区切りで `docs/STATUS.md` を更新する(常に「今」だけを書く)。次の一手が変わる変更では同じコミットに
  含め、セッション終了を待たない
- 実装・レビュー反映の節目ごとに、関心単位でコミットする。未コミットのまま次の節目へ
  進まない(リポジトリ作成直後の初期コミットを含む)

## 安全

- **認証情報・シークレット(パスワード・APIキー・トークン)はどこにも書かない**(hooks の検出は高確度パターンのみの補助)
- **main へのマージ・リリース・公開の判断は人間が行う。** AIは差分とPRの提示まで
- 不可逆な操作(削除・復元不能な上書き・外部への送信・課金)の前は必ず停止し、ユーザーの
  確認を取る(STATUS.md・生きた文書の通常の上書き更新は該当しない)
- 曖昧な点は勝手に埋めず質問する。誤りと思えば根拠を添えて反対する
- テストが通らない状態で「完了」と報告しない。検証をスキップしたときはその旨を明記する
- `AGENTS.md`・`.agents/skills/`・`.claude/`・`.codex/`(hooks・rules・スキル入口)・hooks が参照するスクリプト(`scripts/check-proposal-approved.sh`・`scripts/check-credentials.sh`)の変更は
  自己権限拡大にあたるため、ユーザーの承認なしに行わない
- 複数エージェントで並列作業するときは git worktree でタスクごとに隔離する。ワークスペース配下のリポジトリの
  worktree は、そのワークスペースの `repos/` 直下(例: `repos/<name>-<task>`)に作る
- このファイルは100行以下を保つ。「消したらAIがミスするか?」で No の行は削除し、手順は `.agents/skills/`、パス限定の規約は `docs/rules/` へ逃がす

## ワークスペース配下の場合

このリポジトリが project-workspace(`repos/` 配下)にあるとき、ワークスペースのルールも
併せて適用される(重複時はこのファイルが優先)。ここは独立した git なので、CLI によっては
ワークスペースの `AGENTS.md` を自動では読まない — セッション開始時に `../../AGENTS.md`(このファイル基準)を読む。
打ち合わせ・事業判断・運営の記録はワークスペース側(`journal/`・`docs/`)、
このリポジトリの `docs/` には技術的な記録だけを書く。
リポジトリの状況が進行中案件に影響したら、ワークスペースの `STATUS.md` のポインタ・案件側の次の一手も
更新し(作業の詳細はこのリポジトリの `docs/STATUS.md` が正)、
節目(実装完了・レビュー完了など)はワークスペースの `journal/` にも1行残す。
