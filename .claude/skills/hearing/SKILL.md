# hearing — 要件ヒアリング

計画の質はヒアリングの質で決まる。目標は「チェックリストの全項目が、ユーザーの回答
またはユーザーが承認した提案で埋まっている」状態。推測やデフォルト値で黙って埋めた
項目が1つでも残っていたら、ヒアリングは未完了。

## 進め方の原則

- **1回に1トピックだけ聞く。** 複数の質問を箇条書きで一括送信しない。
  回答を受けてから、その回答が生む次の疑問を掘る
- **選択式にできる質問は選択肢を提示する**(選択式質問ツールが使える環境では積極的に使う)。
  自由回答はユーザーの負担が大きい
- **専門用語で聞かない。** 「RBACは必要ですか?」ではなく
  「管理者と一般ユーザーで、できることを分けますか?」と聞く
- **具体例で確認する。** 抽象的な合意は後でずれる。
  「例えば、田中さんが会議室Aを10時に予約しようとして既に埋まっていたら、どうなるべきですか?」
- **答えは要約して返す。** 「〜という理解で合っていますか?」で認識合わせをしてから次へ
- **「お任せ」への対応**: 丸投げのまま進めず、具体案を1つ作って
  「この内容で進めます。よろしいですか?」と承認を取る。承認された提案は
  「ユーザー確認済み」として扱ってよい(承認は明示的な発言のみ。
  「いいね」「なるほど」等の曖昧な相槌は承認としない)
- **答えられない質問が出たら**: その場で決めさせず「仮案+再検討の条件」を提案して合意を取る

## チェックリスト(全項目を埋める)

順番は目安。会話の流れに合わせて入れ替えてよいが、飛ばさない。
小さめの機能追加では、明らかに無関係な領域(認証・インフラ等)は「変更なし」と確認するだけでよい。

1. **目的** — 誰の・どんな課題を・今はどう処理していて・何ができたら成功か
2. **利用者** — 社内/社外、人数規模、ロール分離の要否、ITリテラシー・利用環境
3. **管理対象(エンティティ)** — 何を管理するか(名詞を拾う)、データ量見込み、データの持ち主
4. **主要ユースケース** — 主要操作を5個前後。CRUD以上のビジネスルール(重複禁止・締切・
   承認フロー・在庫引き当て…)を優先して掘り、例外時の挙動を具体例で確認
5. **認証・アカウント** — ログイン要否、アカウントの作られ方、Google ログイン・2FA 等
6. **外部連携** — メール・通知、決済、既存システム・データとの連携や移行、API公開
7. **非機能要件** — 対応デバイス、多言語、性能・可用性への特別な要求
8. **運用・インフラ** — デプロイ先の希望・制約、予算感、運用者
9. **既存資産** — 既存のコード・デザイン・ドメイン・データ。流用/捨てるの切り分け
10. **スコープ外** — 「今回はやらないこと」の明文化。ここが曖昧だと実装AIが善意で拡大解釈する

## 記録

- 回答は都度 `requirements.md` に反映する。**会話にしかない情報を残さない**
  (セッションをまたぐ伝達はファイルのみ)。置き場:
  - **ワークスペース配下**: 事業要件・リポジトリ横断の要件はワークスペースの
    `docs/requirements.md`、単一リポジトリに閉じる技術要件はそのリポジトリの
    `docs/requirements.md`
  - **リポジトリがまだ無い新規プロジェクト**: ワークスペース側に書き、
    リポジトリ作成後に技術部分を移す
  - **単体リポジトリ(ワークスペースなし)**: リポジトリの `docs/requirements.md`
  - 迷ったら: リポジトリが1つのうちはリポジトリ側に一本化してよい。2つ目のリポジトリが
    できた時点で、横断する要件をワークスペース側へ切り出す
- 全項目が埋まったら requirements.md の全文をユーザーに提示して最終確認を取る。
  修正・違和感は新たなヒアリング項目として掘り直す
- 「仮案+再検討の条件」で合意した項目は `docs/decisions/` に記録し、「再検討の条件」節に
  条件を明記する(ユーザーと合意済みなので `status: stable`。書式は `_template.md`)
- 大きい変更のためのヒアリングなら、結果を `changes/<name>/proposal.md` の
  背景・スコープ・やらないことにも反映する

## requirements.md の構成

```markdown
# 要件

## 目的(誰の・何を・成功の定義)
## 利用者とロール
## 主要エンティティ
## 主要ユースケース(ビジネスルール込み)
## 認証・アカウント
## 外部連携
## 非機能要件(デバイス、規模、性能)
## 運用・インフラ(デプロイ先、予算、運用者)
## 既存資産(流用・移行するもの)
## スコープ外
```

要件は「生きた文書」として維持する — 変更が承認されたら requirements.md を更新し、
常に現在形を保つ(履歴は git と decisions に任せる)。PROJECT.md(安定した短い概要)とは
役割が違う: 詳細な要件・ユースケースの正典は requirements.md、変わらない背景は PROJECT.md。
