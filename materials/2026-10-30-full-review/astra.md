### A-01 / P2: 秘密の保存禁止と、原本・環境設定の手順が食い違う

**箇所:** `materials/README.md:9-10`、`templates/repo/docs/PROJECT.md:23`。対照: `AGENTS.md:55-56`、`templates/repo/AGENTS.md:74`。

**何が起きるか:** 恒常ルールは秘密をワークスペースのどこにも書かないとする。一方で materials は認証情報入り原本について「確認して保存・変換」「変換版だけマスク」と読め、PROJECT の例は `.env.example` をコピーして秘密を入れる手順を示唆する。秘密入り原本を Git 管理の materials に残してよいのか、ローカルの `.env` に実値を置いてよいのか、担当AIが文書ごとに逆の判断をする。第三者の個人情報と認証情報を一つの確認手順に束ねた点も、秘密の禁止が単なる確認待ちに見える原因になる。

**直し方の案:** 秘密と個人情報の扱いを分ける。現行の禁止を維持するなら、秘密入り原本はそのまま保存せず、外部の安全な保管先と秘密を除いた受領版を使う。PROJECT の例も値を取得・保存する指示ではなく秘密管理サービスからの注入方法等へそろえる。人間による Git 管理外 `.env` 作成を許す意図なら、対象主体と許可範囲を正典に明記する。`.gitignore` に入ることだけを保存許可としない。

### A-02 / P2: JSON パーサがないとき、Claude 形式は検査不能を安全側に止めない

**箇所:** `scripts/check-credentials.sh:38-40,51-63`、`scripts/check-proposal-approved.sh:54-55,78-84`。`templates/repo/scripts/` の同名ファイルにも同じ問題。対照: `README.md:170-174`。

**何が起きるか:** README は jq/python3 のどちらもなければブロックすると説明するが、Claude 形式は実際には生 JSON の正規表現走査へ退避する。JSON の文字列を復号できないので、同じ書き込み内容でもエスケープ表現によって判定が変わる。例えば Write の `content` 内で既知トークンの接頭辞の1文字を JSON の Unicode エスケープにした場合、ツールが復号する本文にはトークンがある一方、raw JSON には連続した検出パターンがなく通る。承認ゲートもキーがエスケープされた有効な JSON から `file_path` を拾えないと、paths が空として exit 0 になる。

**直し方の案:** パーサ不在時は両形式とも理由付き exit 2 に統一する。少なくとも「検査できない」と「対象外」を分ける。現行 selftest の「パーサ無し + Claude Write 対象外 → pass」はこの方針では改める。復号が必要な合成 JSON の回帰ケースを追加する。

**根拠の種類:** 静的判定。既存 selftest は raw ASCII のフォールバックのみ確認しており、上の追加ケースは実行していない。現行 CLI がこの表記の JSON を生成する頻度は要確認。

### A-03 / P2: 同一パッチで承認を取り消しても、取り消す前の承認で design/tasks を通す

**箇所:** `scripts/check-proposal-approved.sh:58-74,93-101` (両層)。対照: `templates/repo/changes/_template/proposal.md:35-37`、`templates/repo/AGENTS.md:31-32`。

**何が起きるか:** ディスク上の proposal が承認済みの状態から、1回の apply_patch で (a) proposal のスコープと承認を `[ ]` に更新し、(b) 同じ change の design/tasks を更新しても、ゲートはパッチ内の proposal の変更内容を見ずに旧 `[x]` を読むため通る。終了時には「未承認 proposal に対応する新 design/tasks」が残る。同一パッチ内で新たに承認を付けても根拠にしないケースはテスト済みだが、その逆の失効は扱っていない。

**直し方の案:** 最小案は、対象 change の proposal と design/tasks を同時に更新するパッチをブロックし、proposal の変更と再承認を先に確定させる。精密に扱うなら少なくとも承認の解除・proposal の削除/移動/置換を検出して旧承認を使わない。通常の複数ファイル編集として回帰ケースを追加する。

**根拠の種類:** 静的判定。スクリプト自身が「実行前のディスクだけを見る」と明記している点は認識している。その設計では新規承認の先取りは防げても、既存承認の失効は守れないという指摘。追加パッチは実行していない。

### A-04 / P2: 推奨する worktree 作業では、ワークスペース規範を読む相対パスが保てない

**箇所:** `templates/repo/AGENTS.md:82,84-93`、`README.md:141-144,215-216`。

**何が起きるか:** 並列作業では worktree を必須にする一方、ワークスペース特定はこのファイルから `../../AGENTS.md` のみで、worktree の作成位置に条件がない。元が `/ws/repos/app` でも `/ws/worktrees/app/task` 等に worktree を作れば、このパスは `/ws/worktrees/AGENTS.md` になる。workspace 外へ出した場合は「repos 配下の場合」の条件自体から外れたように読める。元のワークスペースに属するタスクなのに、事業判断・記録先・leader だけが STATUS/journal を書く規則を読めなくなり、再開に必要な運営記録が欠けたり誤った場所に書かれたりする。README が注意する共有スキル消失の回避だけでは、この必読ルールの消失は直らない。

**直し方の案:** 簡単な方法は worktree を `repos/<別名>/` に作る規約を足し、workspace の関係を維持する。任意配置を許すなら、作業依頼/STATUS に元ワークスペースのパスを必ず記録し、その AGENTS と記録先を引き継ぐ。単体リポジトリと「元は workspace 配下の linked worktree」を区別する。
