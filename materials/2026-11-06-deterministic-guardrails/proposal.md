## 前提として守る既存の決定(この提案自身の制約)

1. **2026-09-23「スキルと hooks をベンダー中立にする」(stable)**: 「追加するのは置き場と入口だけ。AI を縛る義務は増やさない」。
   「STATUS 未更新を警告する hook」は義務の追加として取り下げ済み
   → 採る行はすべて「**規則の文言は既にあり、新しい義務は増えない。規則が既に名指ししている人間へ、判断を `ask` で回すだけ**」と
   言えるものに限る。そう言えないものは見送る
2. **2026-07-25「standards.md を置かず、学びは昇格する」(stable)**: hooks への昇格は「learnings のエントリが規範に育ったら」。
   **今回の候補は、learnings に失敗として記録されたものから来ていない**(きっかけは外部の記事で、失敗の観測ではない)。
   予防的に昇格するか、実案件で取りこぼしを観測するまで待つかは**ユーザーの判断**(下の「判断してほしいこと」)
3. 承認ゲート hooks の検査は**編集ツール経路のみ**(両層 AGENTS.md に明記)。シェル経路への拡張は範囲の変更なので、他の候補とは別に判断する

## 採る候補(1・2・3)の共通の形

- 新しいスクリプトは作らず、既存の2スクリプトと同じ流儀(jq → python3、検査できない入力は通さない)で書く。
  1・3 は新しいスクリプト `check-human-gate.sh`(仮)にまとめるか、承認ゲートに足すかは design で決める
- 判定は `ask`。止めるのではなく、規則が既に名指ししている人間に判断を回す。Codex で `ask` が効かない場合は `deny` にして、
  stderr で「ユーザーの承認を得てから再実行してください」と返す
- `hooks-selftest.sh` に各候補のケースを足す(両層)。これも費用に数える

## 実装前に確かめること(提案を止める理由ではない)

- **Claude Code の `ask` の正しい書き方**: ctx7 で確認できたのは、プラグイン例の「stderr に JSON + exit 2」だけ。公式の hooks リファレンスで、
  stdout の `hookSpecificOutput.permissionDecision: "ask"` + exit 0 が正しい形か確かめる
- **Codex の `ask`**: 出力スキーマの選択肢に `ask` があることまでは確認した(`codex-rs/hooks/schema/.../pre-tool-use.command.output.schema.json`)。
  テストで確認されているのは `deny` だけ。実 CLI で `ask` が確認画面になるか、未対応として素通りするかを確かめる
- **権限モードとの関係**: auto・bypass などの権限モードで、hook の `ask` が利用者に届くか
- 既存 hook の実 CLI での挙動が未検証のまま(STATUS の「次の一手」)。新しい hook は同じ未検証分をそのまま引き継ぐ
