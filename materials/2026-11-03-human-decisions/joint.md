# 合意: 「本人の判断」を proposal に入れる方向性(2026-11-03)

[fable.md](fable.md)・[astra.md](astra.md)(保存のまま)。協議は agmsg で2往復。
前提: 記事は BRIEF の要約のみを根拠にし、原文取得・実行検証はしていない。文言確定・実装提案ではなく方向性の評価。
まとめ: review-fable。

## 合意した方向性

両者とも **条件付き賛成**。template-cc 案(案1・案2)を**修正して採る**。

- **問題設定の修正:** 欠けているのは「聞く手順」ではなく「ユーザーの判断の置き場と帰属」。hearing は既に
  未決事項の解消と仮定の明示を要求している(`.agents/skills/hearing/SKILL.md:13-15,19-33`)が、回答は
  背景・スコープに溶ける反映先(同 `:75-76`)で、承認時に AI の補完と区別できない。承認も要旨で残るため、
  後からユーザー発言と AI の補完が区別しにくい(`templates/repo/changes/_template/proposal.md:30-37`)。
  1人+AI では記事の第三者 LGTM とは形が違い、すり抜けるのは AI が自分で置いた仮定と、hearing を通らない
  軽量 proposal(hearing:7-8「小さな修正: 使わない」だが軽量でも承認は必須 `templates/repo/AGENTS.md:23-26`)。
- **節の範囲(案1 の修正):** 「下書き時に AI が決められない 0〜4 点」だけでなく、**この change に関わる
  ユーザーの判断すべて**(hearing の回答・下書き時の問いへの回答、いずれも原文)を置く。既存の stable 決定は
  出所参照で再利用し、再質問・二重管理しない。判断=選択・スコープ境界・任せる範囲に限り、要件の記述は
  従来どおり背景・スコープ・やらないことへ。独立した小節にする(背景等に散らすより出所を見つけやすい)。
  proposal.md は全リポジトリにあり、hearing はワークスペース層のみ(AGENTS.md:21「あれば」)なので、置き場は proposal。
- **案2(承認発言 原文)を採る。** 「いいね」「なるほど」を承認扱いしない現行規則(proposal.md:35-36、hearing:32)は
  維持し、原文はその監査を可能にする。条件付き承認(「OK、ただし X は外して」)は原文の方が確実に残る。

## 条件

1. **AI の役割:** 問いの抽出・下書きと、実回答の**原文転記は可**。回答の**創作・代行(AI が判断を埋める)は禁止**。
   「AI が節を埋めない」の字義どおりでは転記まで禁止になるため、この区別で書く。0 件なら AI が「0件(理由)」と書く。
   AI の仮定・説明は引用と明確に分ける(節内の別行か節外。文言時に決める)。
2. **件数:** 0〜4 は下書き時の**未決の問い**の目安。総件数の上限にしない(5件目の重要事項を捨てない、0件を埋める
   質問もしない)。未決の問いが 4 を超えるのは hearing 未完了の整理の合図(AGENTS.md:20「聞き切る」に戻る)で、
   解決済み判断の記録が 5 件以上でも未完了とはしない。未決 0 件とユーザー判断 0 件は別。聞き方は hearing の
   1トピックずつ(hearing:20-21)に従い、節は記録として扱う。
3. **区分:** 件数を区分基準(AGENTS.md:25-28: 何に触るか+規模+可逆性)に加えない。**0 件を軽量の根拠にしない**
   (ユーザーが事前に全部決めた公開 API 変更は 0 件でも標準)。使うなら「判断が多い軽量は区分を疑う」の片方向のみ。
4. **原文の記録:** 回答原文は問い・選択肢・対象案・日付/出所と対応させる(「Bで」「それで進めて」だけを切り離さない)。
   選択式ツールの回答は選択肢の文言が原文になるので、選択肢提示だったことが分かる形にする。秘密を含む発言は
   複写しない(既存の秘密禁止 AGENTS.md:76 が優先)。
5. **承認:** 判断欄を先に見せても、承認は区分・スコープ・やらないこと・影響範囲を含む **proposal 全体**に対して得る
   (AGENTS.md:24)。判断欄だけの承認を実装許可に広げない。承認原文は対象(どの版・何に対して)と対応させ、
   短い返事と git だけで範囲が一意に決まるとは扱わない。実装中のユーザー判断の変更はその場で停止・再承認
   (AGENTS.md:31-32)し、完了報告で追認扱いにしない。任された範囲の実装詳細は従来どおり質問しない。
6. **事後の照合:** 完了報告「判断した点」(`tasks.md:36`・`proposal.md:50`)に「ユーザーの判断・やらないことと
   照合し、無い判断を書く」の一句を足す(記事の新 Gap Report 2点目に相当)。lens-review は変更しない
   (`tasks.md:20-22` が既に「判断した点」を照合対象として lens-review に委ねている)。
7. **hooks:** 変更なし。案2 は `scripts/check-proposal-approved.sh:123`(両層同一)が行頭 `- [x] ユーザー承認` だけを
   見るため、接頭部を維持すれば判定に影響しない — 静的評価に限る(`hooks-selftest.sh:6,29,31` の fixture も「要旨」を
   含まない)。hook は原文の存在・真正性・意味を検証しない。実 CLI での挙動は未確認(STATUS「次の一手」と同じ)。
8. **影響箇所と行数(概算):**

   |---|---|---|
   | `templates/repo/changes/_template/proposal.md`(52行) | 判断の小節+原文記録の注意。承認欄を原文に | +8〜12 |

9. **要確認:** この template の実運用で LGTM 化は**未観測**(両層 `docs/learnings.md` 本文は空)。記事の次案も未実践で、
   複数人チームの結果を 1人+AI にそのまま適用しない。予防的かつ安価・可逆な変更として採り、次の実案件で
   「既存回答の聞き直し」「AI の勝手な補完」が減るかを dev-log に残す。新しい定例・計測制度は作らない。

## 割れた点(協議で解消)

- **照合の置き場:** fable=完了報告「判断した点」/ astra=lens-review correctness → 完了報告側に1句、lens-review 不変(条件6)。
- **「4超」の意味:** fable=hearing 未完了の合図 / astra=総上限にしない → 未決の問いの数だけを合図にし、記録数には適用しない(条件2)。
- **承認範囲の根拠:** fable=原文+その時点の proposal と git / astra=短い返事と git だけで一意とは扱わない → 原文を対象と対応させる(条件5)。
- **節の範囲:** template-cc 案は下書き時の問いのみ。astra=回答済みの判断も対象、fable=hearing:75-76 の反映先を節へ → 同旨。
  節は change に関わるユーザーの判断すべて(「合意した方向性」)。

## 見送るもの

- 事後共有・定例、3レベル・Issue ラベル、AI ループ(template-cc の見送りに賛成)。
- 記事の「事前確認は Decisions だけ」: 採らない。承認は proposal 全体(条件5)。
- 記事の「判断の有無でレベルを決める」: 採らない。現行の区分基準を維持(条件3)。
- 「コードから見えない外部事情の抜け」の事前確認の儀式化: hearing の守備範囲で足りる。
- lens-review への追記、新たな規約ファイル・レビュー工程、ワークスペース層への proposal/承認欄の複製
  (ワークスペースの同等物は docs/decisions の stable=ユーザー承認と journal の「決定」で足りる)。
- 記事の「人のコードレビュー廃止」を AI 観点レビュー・テストの削減に広げない(AGENTS.md:29-30、tasks.md:15-22)。
- 注記: ループの「期限」と decisions の「再検討の条件」(`docs/decisions/_template.md:7,55-57`)は同義ではない
  (後者は見直し条件で、期限到来時の停止を保証しない)。将来ループを導入するなら終了期限・停止の人の判断を別途定める。今は機構を足さない。
